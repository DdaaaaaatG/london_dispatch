> 작성 2026-10-08 · system-architect · 단계 ②/③ · 상태 **승인 ① 완료**(2026-10-08 — Q1~Q5 답변 반영, §8.1 U6~U10 · §15)
> 근거 `s6-01-구조분석.md`. 계층 세부 규칙은 server-design-strategy · contract-design-strategy · ui-design-strategy를 따른다(재정의 없음).

## 0. 범위·결론

비유: 잠긴 방 문 앞에는 번호 자물쇠가 있다. 번호를 맞히면 사서가 **그 방 전용 도장**을 찍어 주고, 브라우저는 그 도장을 수첩에 적어 둔다. 자물쇠 번호를 바꾸면 옛 도장은 모두 무효가 된다. 관장(갠홈 주인)은 번호 없이 도장을 받는다.

- 서버는 비밀번호를 **해시로만** 저장한다(`rooms.pass_hash`, 마이그레이션 0005, 칸 1개 추가).
- 비밀번호를 맞히면 서버가 **입장 증명(entry key)** 을 준다. 증명 = `HMAC(파생 키, 방 id + 현재 해시)`. 서버에 따로 저장하지 않고 요청마다 다시 계산해 맞춘다(무상태).
- 비밀번호를 바꾸거나 풀면 해시가 바뀌므로(매번 새 salt) **옛 증명은 자동으로 무효**다. 버전 칸이 필요 없다.
- 화면은 증명을 `localStorage`(try/catch)에 방별로 기억하고 요청 헤더 **`X-Room-Key`** 로만 보낸다. 회원 토큰은 지금처럼 메모리에만 둔다.
- 잠긴 방의 **내용과 관리**(E5~E14, 새 E18·E19)는 증명이 있거나 요청자가 주인일 때만 통과한다. 그 밖은 `403 ROOM_LOCKED`.
- 방 목록(E3)은 계속 누구나 본다. 행에 `locked: boolean`만 더한다(결정 ①). **화면은 잠긴 행에 제목과 자물쇠만 그리고 마지막 대화 날짜는 그리지 않는다**(U8). 응답 필드(`updatedAt` 포함)는 그대로다 — 계약 비파괴.
- 주인 프리패스(결정 ③)는 **입장 엔드포인트가 비밀번호 없이 증명을 내주는 것**으로 구현한다. 그래서 읽기 경로 E7은 지금처럼 토큰을 보지 않는다(api.md §2.1 약속 유지).
- 엔드포인트 3개 신설(입장 · 비밀번호 설정/변경 · 해제) + E4 확장. 에러 코드 2개 신설. env 키 1개(비밀 아님). 토큰·PHP 조각은 그대로 — **저쪽 재배포 없음**.

## 1. 데이터

### 1.1 스키마 (마이그레이션 0005 — 문안은 server-designer 확정)

```sql
-- 0005_room_password.sql
ALTER TABLE rooms ADD COLUMN pass_hash TEXT
  CHECK (pass_hash IS NULL OR length(pass_hash) BETWEEN 20 AND 200);
```

| 칸 | 의미 | 기본값 | 이관 |
|---|---|---|---|
| `pass_hash` | NULL = 잠기지 않음. 값 = 비밀번호 해시 문자열 | NULL | 없음 — 기존 방은 전부 잠기지 않음(R-LOCK-009) |

- DROP·타입 변경 없음. 이전 코드는 이 칸을 모르고 동작한다(되돌리기 위험은 §13).
- `locked`는 칸이 아니라 투영이다: 목록·요약 SELECT에 `(r.pass_hash IS NOT NULL) AS locked`. 해시는 db 밖으로 나가지 않는 응답 경로를 둔다(`RoomSummary`에 해시 없음).

### 1.2 해시 형식

```
pbkdf2-sha256$<반복 수>$<salt base64url 16바이트>$<유도값 base64url 32바이트>
```

- Web Crypto `crypto.subtle.deriveBits({ name: 'PBKDF2', hash: 'SHA-256', salt, iterations }, …, 256)`. 새 패키지 없음.
- salt는 설정·변경 때마다 `crypto.getRandomValues`로 새로 만든다. 같은 비밀번호로 다시 설정해도 해시가 바뀐다 → 옛 증명 무효(§2).
- **반복 수를 문자열에 기록**한다. 검증은 저장된 반복 수를 쓰므로 나중에 상수를 올려도 마이그레이션이 없다.
- 반복 수 초기값은 **Free 요금제 기준으로 확정**(U10): server-implementer가 해시 1회 CPU **≤ 5ms**(Free 10ms 한도의 절반)가 되는 값을 실측으로 정한다. workerd 상한은 100,000회다. 근사 측정은 Node 22 `crypto.subtle` 1회 벤치, 확인은 운영 배포 뒤 Cloudflare 대시보드 CPU 시간.
- 나중에 Paid로 확인되면 **반복 수 상수만 올린다.** 새로 설정·변경되는 비밀번호부터 새 값이 쓰이고, 이미 저장된 해시는 기록된 옛 반복 수로 계속 검증된다(마이그레이션·재설정 없음).
- 비교는 `crypto.subtle.timingSafeEqual`(token.ts와 같은 방식).

### 1.3 비밀번호 규칙

| 규칙 | 값 |
|---|---|
| 길이 | 코드 포인트 **4~32**(`Array.from(s).length`, rooms 제목 규칙과 같은 단위). **확정(U6)** — 화면 안내 「6자 이상 권장」 |
| 정규화 | **하지 않는다**(trim 없음). 받은 그대로 해시한다 |
| 문자 | 제한 없음 |
| 위반 문구 | `비밀번호는 4~32자로 입력해 주세요.` |
| 상수 위치 | shared `limits.ts` `ROOM_PASSWORD_MIN`·`ROOM_PASSWORD_MAX`(화면 카운터와 서버 판정이 같은 값) |

## 2. 입장 증명 (entry key)

### 2.1 만드는 법

```
파생 키 K = HMAC-SHA256(key = TOKEN_SECRET, msg = "london_dispatch/room-entry/v1")    // 컨테이너에서 1회
증명    = "e1." + base64url( HMAC-SHA256(K, roomId + "\n" + pass_hash) )              // 46자
```

- `TOKEN_SECRET`을 **그대로 쓰지 않고 용도 문자열로 파생**한다(도메인 분리). 토큰 서명과 증명이 서로를 대신할 수 없다.
- `"e1."` 접두사는 형식 버전이다. 형식을 바꾸면 `e2.`로 올리고 옛 증명은 무효(다시 묻기)로 둔다.

### 2.2 검증·수명

| 항목 | 규칙 |
|---|---|
| 받는 곳 | 요청 헤더 `X-Room-Key` **하나뿐**. 쿼리·본문·쿠키는 보지 않는다(로그·Referer 노출 방지) |
| 검증 | 대상 방의 **현재** `pass_hash`로 다시 계산해 `timingSafeEqual`. 길이 128 초과·형식 불일치 = 무효(400이 아니라 무효로 본다) |
| 수명 | **만료 없음**(결정 ②). 무효가 되는 경우는 셋: 비밀번호 변경 · 잠금 해제(뒤 재설정 포함) · `TOKEN_SECRET` 교체 |
| 범위 | 방 하나. 다른 방 요청에 붙여도 그 방 해시와 맞지 않으므로 무효 |
| 서버 저장 | 없음. 세션 테이블·발급 기록 없음 |
| 로그·응답 | 증명 값·해시·비밀번호를 어디에도 남기지 않는다 |

### 2.3 화면 보관 (ui `state/roomKeys.ts` 신규)

| 항목 | 규칙 |
|---|---|
| 위치 | `localStorage` 키 `ld:roomKeys` 하나에 `[roomId, entryKey]` 쌍 배열(JSON). 접근은 `components/utils/storage.ts` 경유(try/catch) |
| 저장 실패 | 같은 세션 메모리 Map에만 둔다(새로 열면 다시 묻는다) |
| 상한 | 50쌍. 넘으면 가장 오래 저장한 것부터 버린다 |
| 비었을 때 | 키 자체를 지운다(잠긴 방을 안 쓰는 사용자의 저장소는 지금과 같다 — 기존 단언 `['ld:lastRoomId']` 유지) |
| 지우는 때 | `ROOM_LOCKED` 응답을 받은 그 방 · 방 삭제 성공 · 잠금 해제 성공 |
| 토큰과의 관계 | **증명은 토큰이 아니다.** 토큰은 계속 `state/token.ts` 메모리에만 있다(R-CHAT-009 🔒 불변) |

## 3. 접근 관문 (방 입장 판정 — 한 곳)

### 3.1 규칙

```
대상 방을 찾는다(경로 :id 또는 메시지 id → room_id)
  ├ 방 없음 / 메시지 없음 → 통과(뒤에서 기존 404)
  ├ pass_hash IS NULL → 통과
  ├ principal 있음 && auth.isOwner(principal) → 통과            (결정 ③, 토큰 경로만)
  ├ X-Room-Key 가 현재 해시로 맞음 → 통과
  └ 그 밖 → 403 ROOM_LOCKED
```

- 판정 함수는 server rooms 모듈 하나(`assertEntry`)다. 화면은 판정하지 않고 응답 코드로만 반응한다.
- 라우트에는 미들웨어 `requireRoomEntry('room' | 'message')` 한 줄만 더한다. 서비스 시그니처(`listMessages`·`speak` 등)는 바뀌지 않는다.
- 비용: 요청마다 D1 PK 조회 1회(메시지 경로는 메시지 PK → 방 PK 조인 1회).

### 3.2 적용 표

| # | 경로 | 미들웨어 순서(관문 위치 ★) | 주인 통과 |
|---|---|---|---|
| E5 · E6 | `PATCH`·`DELETE /api/rooms/:id` | requireToken → rateLimitWrites → validate(param) → ★room → (json) | ○ |
| E7 | `GET /api/rooms/:id/messages` | validate(param) → ★room → validate(query) | ✕(토큰 안 봄 — 주인도 증명으로) |
| E8 · E9 | `POST /rooms/:id/user` · `/speak` | requireToken → rateLimitWrites → validate(param) → ★room → validate(json) | ○ |
| E10 · E11 · E12 | `/api/messages/:id` · `/regenerate` | requireToken → rateLimitWrites → validate(param) → ★message → (json) | ○ |
| E13 | `GET /rooms/:id/memory` | requireToken → validate(param) → ★room | ○ |
| E14 | `PUT /rooms/:id/memory` | requireToken → rateLimitWrites → validate(param) → ★room → bodyLimit → json | ○ |
| E18 · E19 | `PUT`·`DELETE /rooms/:id/password`(신규) | requireToken → rateLimitWrites → validate(param) → ★room → (bodyLimit → json) | ○ |

- 순서의 결과: 잠긴 방에 잘못된 쿼리·본문을 보내면 `400`보다 `403 ROOM_LOCKED`가 먼저다(내용 형식 힌트를 주지 않는다). 토큰 실패는 지금처럼 관문보다 먼저다.
- E3·E4·E17·E1·E2·E15·E16에는 관문이 없다.

### 4.1 엔드포인트

| 신규 E17 | `POST /api/rooms/:id/enter` | 입장 — 비밀번호 검증 → 증명 | 추가 | 없음 | rooms·chat |
| 신규 E18 | `PUT /api/rooms/:id/password` | 잠금 설정·비밀번호 변경 | 추가 | 없음 | chat ⋯ |

| 확장 E4 | `POST /api/rooms` 본문 `password?` · 응답 `entryKey` | 생성과 동시에 잠금 | 추가(비파괴) | 없음 | rooms 새 방 |

| 확장 | 요청 헤더 `X-Room-Key` | E5~E14·E18·E19가 읽음 | 추가(없으면 잠기지 않은 방은 지금과 같다) | 없음 | ui/api client |
| 의미 추가 | E5~E14 | 잠긴 방이면 `403 ROOM_LOCKED` 가능 | 비파괴(기존 방은 잠기지 않음) | 없음 | chat |

- **확장 vs 신규 판정**: 입장은 기존에 비슷한 엔드포인트가 없다(비밀번호 검증 + 토큰 선택이라는 새 성질) → 신규. 설정·해제를 E5(`PATCH` 이름 변경)에 얹으면 `title` 필수를 풀어야 해 기존 의미가 바뀐다(파괴) → 신규 하위 경로 `/password`. `PUT` 하나에 `null` = 해제를 섞는 안은 의미가 섞여 기각. 생성은 E4 확장(생성과 잠금을 한 문장 INSERT로 원자 처리).

### 4.2 E17 `POST /api/rooms/:id/enter` — 입장

| 항목 | 값 |
|---|---|
| 토큰 | **선택**. 헤더가 있으면 검증하고, 실패(401·403 사유)면 **익명으로 본다**(거절하지 않는다). 미들웨어 `optionalToken`(신규) |
| 본문 | `EnterRoomBody = { password?: string }`. `password`는 문자열·코드 포인트 64 이하(해시 비용 상한, 넘으면 `400`). 본문 상한 1KiB |
| 판정 순서 | ① 방 없음 → `404 NOT_FOUND` ② 잠기지 않음 → `200 { entryKey: null }` ③ 주인 → `200 { entryKey }`(비밀번호 무시, 시도 미계수) ④ `password` 없음 → `403 ROOM_LOCKED` ⑤ 방 단위 시도 계수(§5) 초과 → `429 RATE_LIMITED` ⑥ 해시 불일치 → `403 ROOM_PASSWORD_WRONG` ⑦ 일치 → `200 { entryKey }` |
| 응답 | `EnterRoomResponse = { entryKey: string \| null }` |
| 부수 효과 | `rate_limits` 키 `enter:{roomId}` 1 증가(⑤ 이후만). 로그 `room_enter_failed{roomId}`(⑥) · `room_enter_limited{roomId}`(⑤) |
| 레이트리밋 | 회원 쓰기 상한(`rateLimitWrites`)은 걸지 않는다(토큰 선택이라 키가 없을 수 있다) |

### 4.3 E18 `PUT /api/rooms/:id/password` — 잠금 설정·변경

| 항목 | 값 |
|---|---|
| 토큰 | 필수. 잠긴 방이면 관문(주인 또는 증명 — U9) |
| 본문 | `SetRoomPasswordBody = { password: string }` — §1.3 규칙. 본문 상한 1KiB |
| 응답 | `200` `SetRoomPasswordResponse = { room: RoomSummary, entryKey: string }` — 바꾼 사람의 브라우저는 다시 묻지 않는다 |
| 에러 | api.md §4.5 쓰기 공통 + `VALIDATION_ERROR`(비밀번호 문구) · `NOT_FOUND` · `ROOM_LOCKED` |
| 부수 효과 | `pass_hash` 교체 → 그 방의 옛 증명 전부 무효. `updated_at` **불변**(목록 순서 = 대화 움직임, D-ROOM-4와 같은 원칙). 로그 `room_password_set{roomId, mbId, wasLocked}` |

### 4.4 E19 `DELETE /api/rooms/:id/password` — 잠금 해제

| 항목 | 값 |
|---|---|
| 토큰 | 필수. 잠긴 방이면 관문(주인 또는 증명 — U9) |
| 응답 | `200` `RoomSummary`(`locked: false`). 이미 풀린 방도 `200`(멱등) |
| 에러 | api.md §4.5 쓰기 공통 + `NOT_FOUND` · `ROOM_LOCKED` |
| 부수 효과 | `pass_hash = NULL`. `updated_at` 불변. 로그 `room_password_cleared{roomId, mbId}` |

### 4.5 E4 확장 `POST /api/rooms`

| 항목 | 값 |
|---|---|
| 본문 | `CreateRoomBody = { title: string; password?: string }`. `password`가 있으면 §1.3 규칙(빈 문자열도 위반). 검사 순서 제목 → 비밀번호 |
| 응답 | `201` `CreateRoomResponse = RoomSummary & { entryKey: string \| null }` — 비밀번호를 걸었으면 증명, 아니면 `null` |
| 원자성 | INSERT 한 문장에 `pass_hash`까지 넣는다. 잠기지 않은 채 잠깐 존재하는 틈이 없다 |

### 4.6 에러 코드

| 코드 | status | 기본 문구 | 화면 처리 |
|---|---|---|---|
| `ROOM_LOCKED` | 403 | `이 방은 비밀번호로 잠겨 있습니다.` | 저장된 증명 삭제 → 입장 재요구(§6). `isAuthFailure`에 **넣지 않는다**(읽기 전용 전환 아님) |

## 5. 무차별 대입 완화

**결론: 기존 `RATE_LIMIT_PER_MIN`으로는 부족하다. 방 단위 분당 상한을 새로 둔다.**

| 근거 | 내용 |
|---|---|
| 기존 상한의 범위 | `rateLimitWrites`는 토큰 회원의 `mbId` 키이고 쓰기 라우트에만 붙는다. 비밀번호 입장은 토큰 없는 열람자가 하므로 키가 없다 |
| 새 상한 | `rate_limits` 테이블 재사용, 키 `enter:{roomId}`, 분 창(기존 `windowStartOf`), 한도 env `ROOM_ENTER_LIMIT_PER_MIN`(기본 **5**, 1~60 — **확정 U7**). **해시 계산 앞에서** 센다 → CPU 남용도 함께 막는다 |
| 세지 않는 것 | 주인 프리패스(③) · 잠기지 않은 방 · 비밀번호 없는 요청(④) — 해시를 하지 않는 경로 |
| 계산 | 분당 5회면 숫자 4자리(1만 가지)는 최악 2,000분(약 33시간), 평균 17시간의 쉬지 않는 시도로 뚫린다. 숫자 6자리는 최악 약 139일. 영문+숫자 6자 이상은 사실상 불가 |
| 그래서 | 화면 안내문에 「6자 이상 권장」을 넣는다. 최소 길이는 4자로 확정(U6) |
| 부작용 | 공격 중에는 그 방의 정상 열람자도 그 1분 동안 `429`를 본다. 주인은 영향 없음. 하루 누적 잠금처럼 더 센 제한은 넣지 않는다(U7 — 장난으로 남의 입장을 하루 막는 것을 피한다) |
| 기각 | IP 단위 상한(IP 저장 = 개인정보, 공유 IP 오탐) · 증명 시도 상한(증명은 256비트 HMAC라 맞혀서 뚫을 수 없다) |
| 감시 | 로그 `room_enter_failed`·`room_enter_limited`(방 id만)로 `wrangler tail`에서 시도를 본다 |
