# S6 구조 분석서 — 방 비밀번호 잠금

> 작성 2026-10-08 · system-architect(읽기 전용) · 단계 ①/③ · 다음: `s6-02-전반설계.md` → `s6-03-인계패킷.md`
> 기준 `c10b49b`(등급 문구 동기화) · 작업 트리 깨끗. 분석가 전수 감사는 생략하고(위임문 허용) 아키텍트가 설계 문서와 소스를 직접 읽었다.
> 요구 원문(사용자 지정 🔒 2026-10-08 저녁): 방을 만들 때 비밀번호를 걸 수 있다(선택). 기존 방도 도중에 잠금 설정·비밀번호 변경·잠금 해제 가능. 결정 ① 목록에 제목 + 자물쇠, 탭 → 비밀번호 → 입장 · 결정 ② 한 번 맞추면 브라우저가 기억, 비밀번호가 바뀌면 다시 묻는다 · 결정 ③ 갠홈 주인은 비밀번호 없이 프리패스, 해제·변경도 가능.

비유: 지금 방은 열람실 서가에 꽂힌 공책이다. 누구나 펼쳐 볼 수 있다. S6은 일부 공책에 **번호 자물쇠**를 다는 일이다. 표지(제목)는 계속 보이고, 번호를 맞히면 사서가 **그 공책 전용 출입 도장**을 손등에 찍어 준다. 도장은 자물쇠 번호를 바꾸면 효력이 없어진다. 관장(갠홈 주인)은 도장 없이도 들어간다.

## 1. 현재 흐름

### 1.1 방 목록·입장 (읽기, 토큰 없음)

```
App(useRoomsLoader) ─ listRooms() ─▶ GET /api/rooms (E3, 토큰 무시) ─▶ rooms.listRooms() ─▶ db SQL_ROOMS_LIST
   └ RoomSummary { id, title, createdAt, updatedAt, messageCount }  — 방 행 전체 공개
   └ lastRoomId(localStorage 'ld:lastRoomId')가 있으면 그 방으로 자동 진입(R-ROOMS-004)
행 탭 → App view = chat(room) ─ listMessages(roomId) ─▶ GET /api/rooms/:id/messages (E7, 토큰 무시) ─▶ messages.listMessages
```

- 방 단건 조회 엔드포인트는 없다. chat은 목록에서 받은 `RoomSummary`를 들고 들어간다(api.md §4.0).
- **읽기 경로는 토큰을 보지 않는다**(api.md §2.1 — 헤더가 있어도 무시, 잘못된 토큰이어도 거절하지 않는다). ui 읽기 래퍼도 헤더를 붙이지 않는다(`client.ts` `auth` 옵션이 `true`일 때만 Bearer).
- 예외: E13 `GET memory`는 읽기지만 `requireToken`이 붙어 있다. E15는 토큰 + 주인.

### 1.2 쓰기·생성 (토큰 필요)

| 경로 | 미들웨어 순서 (server/src/routes) | 대상 방을 아는 방법 |
|---|---|---|
| E4 `POST /api/rooms` | requireToken → rateLimitWrites → validate(json `{title}`) | 새로 만든다 |
| E5·E6 `PATCH`·`DELETE /api/rooms/:id` | requireToken → rateLimitWrites → validate(param) (→ json) | 경로 `:id` |
| E8 `POST /rooms/:id/user` · E9 `POST /rooms/:id/speak` | requireToken → rateLimitWrites → validate(param) → validate(json) | 경로 `:id` |
| E10·E11 `PATCH`·`DELETE /api/messages/:id` · E12 `POST /messages/:id/regenerate` | requireToken → rateLimitWrites → validate(param) (→ json) | **메시지 id뿐** — 방은 서비스가 메시지를 읽어야 안다 |
| E13·E14 `GET`·`PUT /rooms/:id/memory` | requireToken (→ rateLimitWrites → bodyLimit → json) | 경로 `:id` |

- 쓰기 권한은 `TOKEN_MIN_LEVEL`(현재 10 = 갠홈 관리자)뿐이다. rooms 서비스는 `Principal`을 받지 않는다(rooms.md D-ROOM-5).

### 1.3 주인 판정 (S3c)

```
server: auth.isOwner(principal) = principal.mbId ∈ config.ownerMbIds (빈 목록 = 아무도 아님, 닫힌 쪽)
        requireOwner 미들웨어 = requireToken 뒤에서 assertOwner → 403 OWNER_ONLY  (E15·E16 전용)
ui:     App 첫 렌더 뒤 토큰이 있으면 getCharacterSettings(E15) 1회 → 200이면 isOwner (useOwner, F-RM-24)
```

- 주인 판정 함수는 이미 서버에 하나 있다(`auth/service.ts` `isOwner`). S6은 이것을 **재사용**한다. 화면은 토큰을 해석하지 않고 주인 여부를 E15 status로만 안다(api.md §2.7).

### 1.4 레이트리밋

```
rateLimitWrites (requireToken 뒤) → auth.hitRateLimit(principal.mbId)
  → db.rateLimits.hit(key = mbId, windowStart = floor(now/60000)*60000, limit = RATE_LIMIT_PER_MIN 20)
  → SQL_RATE_LIMITS_HIT: INSERT … ON CONFLICT DO UPDATE SET count = count + 1 WHERE count < limit RETURNING count
  → null 이면 429 RATE_LIMITED(retryAfterSec)
```

- 키는 `rate_limits.mb_id TEXT` 한 칸이다. 그누보드 `mb_id`는 영문·숫자·밑줄뿐이라 `:`가 들어간 키(예: `enter:{roomId}`)와 겹치지 않는다.
- **토큰 없는 요청에는 레이트리밋이 없다.** 키가 될 `mbId`가 없기 때문이다.

### 1.5 화면 저장소·토큰

| 항목 | 위치 | 규칙 |
|---|---|---|
| 토큰 | `ui/src/state/token.ts` 모듈 클로저 | 메모리만. localStorage·쿠키 금지(R-CHAT-009 🔒) |
| localStorage 단일 접근 | `ui/src/components/utils/storage.ts` | try/catch, 실패 시 null·무시 |
| 저장 키 | `ld:lastRoomId` + 스크롤 위치 | chat 시나리오가 "키 목록 = `['ld:lastRoomId']`"를 단언한다(`chat/test/scenarios.md` 18행) |
| api 클라이언트 | `ui/src/api/client.ts` | `configureClient({ getToken })` getter 슬롯 하나. `RequestOptions = { method, body, auth }`. `isAuthFailure` = TOKEN_REQUIRED·TOKEN_INVALID·LEVEL_TOO_LOW → 읽기 전용 전환 |

### 1.6 화면 구성 (현재)

```
RoomsScreen: TopBar(ROOMS · [⚙ 주인] · [+ 새 방 토큰]) / NewRoomRow(B 52px: [제목 0/60][취소][만들기]) / RoomList > ListRow(56px: 제목 · MM.DD) / Toast
ChatScreen:  ChatTopBar(‹ · 제목 · MM.DD · ⋯ 토큰) / MessageList / Composer·캐릭터 버튼(토큰)
   ⋯ → RoomMenuSheet(BottomSheet): 이름 변경(PromptSheet) · 장기기억(MemorySheet) · 방 삭제(ConfirmDialog) · 취소
공용 ui: TopBar · Button · IconButton · StateView · TextInput · TextArea · Toggle · BottomSheet · ConfirmDialog · PromptSheet · Toast
```

- `TextInput` Props에 `type`이 없다(항상 text). `PromptSheet`도 입력 종류를 고를 수 없다. 비밀번호 입력에는 공용 델타가 필요하다.
- 자물쇠 아이콘은 공용에 없다(IconButton 아이콘은 `more`·`settings` 등).

### 1.7 DB (현재 `rooms`)

```sql
rooms (id TEXT PK, title TEXT 1~60, created_at, updated_at, speaking_until INTEGER NULL)  -- 0001
```

- `speaking_until`은 **발화 잠금**(speak 중복 방지, R-MSG-007)이다. 코드·문서에 "잠금(lock)"이 이미 이 뜻으로 쓰인다(`SQL_ROOMS_ACQUIRE_SPEAK_LOCK` 등). S6 이름이 겹치면 혼동한다.

### 1.8 env 키 (관련분)

`TOKEN_SECRET`(Secrets, 32자 이상) · `TOKEN_MIN_LEVEL=10` · `RATE_LIMIT_PER_MIN=20` · `OWNER_MB_IDS` · `ALLOWED_FRAME_ANCESTORS`. 모두 `env.ts parseEnv` 단일 진입.

## 3. 문제점·제약·위험

| # | 문제·제약 | 설계에 주는 영향 |
|---|---|---|
| P1 | 읽기 경로(E7)는 토큰을 보지 않는다(§2.1 약속) | 주인 프리패스를 E7에서 토큰으로 판정하면 이 약속을 깬다. **입장 증명 하나로 통일**하고 주인은 "비밀번호 없이 증명을 받는 사람"으로 만들면 E7은 토큰을 계속 안 봐도 된다 |
| P2 | 토큰 없는 요청엔 레이트리밋 키가 없다(§1.4) | 비밀번호 입장 시도에는 **방 단위 키**(`enter:{roomId}`)가 필요하다. 기존 `RATE_LIMIT_PER_MIN`(회원 단위, 쓰기 전용)으로는 막지 못한다 |
| P3 | 메시지 id 경로(E10·E11·E12)는 방을 모른다 | 관문이 메시지 → 방을 한 번 조회해야 한다(PK·인덱스 조회 1회) |
| P4 | 서비스 간 import 금지, rooms는 auth를 모른다(rooms.md §3) | 주인 판정은 컨테이너가 `auth.isOwner`를 함수로 주입하거나 미들웨어가 판정 결과(boolean)를 넘긴다 |
| P5 | Workers CPU 한도(무료 요금제 요청당 10ms 수준, 요금제 미확인 — 지인 계정) | PBKDF2 반복 횟수를 크게 잡으면 입장·설정 요청이 CPU 초과로 죽는다. workerd는 PBKDF2 반복 100,000회가 상한이다. **반복 수를 해시 문자열에 기록**해 나중에 올릴 수 있게 하고, 처음 값은 실측(검증 ≤ 5ms)으로 정한다 |
| P6 | 증명 유출 | localStorage는 같은 출처 스크립트가 읽을 수 있다. 증명이 새면 비밀번호를 바꿀 때까지 열린다. 증명은 URL·로그에 싣지 않고 헤더로만 보낸다. 대응은 "비밀번호 변경 = 모든 증명 무효" |
| P7 | 제3자 iframe 저장소 | 갠홈(`london-gossip.my`) 안의 `*.workers.dev` iframe은 브라우저가 저장소를 상위 사이트별로 나누고, Safari는 일정 기간 뒤 지울 수 있다. 결정 ②의 "기억"이 브라우저 정책으로 풀리면 다시 묻는다(기존 `lastRoomId`와 같은 성질) |
| P8 | 용어 충돌 | "잠금"이 이미 발화 잠금(`speaking_until`)을 뜻한다. S6 코드 이름은 `password`·`entry`로 짓고, 응답 필드만 `locked`로 둔다 |
| P9 | 🔒 개수 고정 요구 | 엔드포인트 16 → 19, 에러 코드 15 → 17. 메인 세션의 요구 개정이 승인 ①에 들어가야 한다 |
| P10 | 되돌리기 위험 | 마이그레이션 뒤 코드를 이전 커밋으로 되돌리면 이전 코드는 새 칸을 모르므로 **잠긴 방이 모두 열린다.** 되돌리기 절차서에 경고를 적는다 |
| P11 | 배포 순서 | 목록 SELECT가 새 칸을 읽는다. 코드가 마이그레이션보다 먼저 올라가면 E3부터 `500`. `/deploy` 순서(마이그레이션 → deploy)를 지킨다(S3f와 같다) |
| P12 | 주인 판정 재사용 | `OWNER_MB_IDS`가 비면 아무도 프리패스가 아니다(닫힌 쪽). 토큰 등급이 `TOKEN_MIN_LEVEL` 미만이면 `authenticate`가 실패하므로 주인이어도 프리패스가 안 된다 — 지금 주인은 등급 10이라 문제없다 |

## 4. 상태 흐름 (현재 — 방 접근)

| 상태 | 진입 이벤트 | 전이 | 잠금 |
|---|---|---|---|
| 목록 | 앱 시작(lastRoomId 없음) · ‹ 뒤로 | 행 탭 → 대화 | 없음 |
