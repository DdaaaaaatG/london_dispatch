# S3f 전반 설계서 — 설정 화면에서 Gemini 모델(Pro / Flash) 선택

> 작성 2026-10-07 · system-architect · 단계 ②/③ · 상태 **승인 ① 대기**(§9 L1~L10 · §10 신규 2건 · §14 Q1~Q5)
> 근거 `s3f-01-구조분석.md`. 계층 세부 규칙은 각 설계 전략 스킬을 따른다(재정의 없음).
> 작업 모드: **보강**(S3c 설정 화면·E15·E16이 이미 있다).

## 0. 범위·결론

- 갠홈 주인이 설정 화면 **「공통」 탭 맨 위**에서 「Pro」·「Flash」 중 하나를 고르고, **기존 「저장」 버튼**으로 함께 저장한다.
- 저장소는 `character_settings` 행에 **칸 1개**(`llm_model`, 마이그레이션 0004)를 더한다. 설정 본체 JSON에는 넣지 않는다.
- 계약은 **E15·E16 확장**(응답 `model` 추가, 본문 `model?` 추가)이다. 엔드포인트·에러 코드·env 키·토큰은 늘지 않는다.
- 모델은 **요청마다** D1에서 읽어 정한다. 저장 즉시 다음에 시작하는 발화·화자 선택·요약 호출부터 바뀐다(캐시 없음, S3c와 같은 패턴).
- 단가는 **모델별 단가표**(server 상수)에서 고른다. env `LLM_PRICE_*`는 표 밖 모델의 폴백이다.
- 제공사가 오류를 내도 **다른 모델로 자동 전환하지 않는다**(2026-10-06 사용자 지시 "몰래 가벼운 모델로 바꾸기 금지").
- 화면·응답은 키(`'pro'`·`'flash'`)만 안다. 실제 모델명은 server 상수 한 곳에만 있다. Google이 이름을 바꾸면 상수만 고친다.

## 1. 결정 1 — 저장소

| 안 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| A | 설정 본체 JSON(`settings`)에 `model` 키 추가 | 마이그레이션 없음 | R-SET-002 strict 본체가 바뀐다. 내보내기 화이트리스트·가져오기 매핑·`checkCharacterSettings` 문구 순서가 모두 흔들린다. 운영 설정이 캐릭터 파일로 새어 나갈 위험 | 기각 |
| **B** | `character_settings`에 `llm_model TEXT NULL` 칸 추가 | 저장 버튼 1회 = UPSERT 1문장(원자). 같은 주인 권한·같은 version. 마이그레이션이 `ADD COLUMN` 1줄이고 기존 행 보존. 새 repo 파일 0 | 이름이 "캐릭터 설정"인 행에 운영 설정 1칸이 같이 산다 | **권고** |
| C | 새 테이블 `app_settings`(id = 1, `llm_model`, …) | 의미가 깔끔하고 운영 설정이 늘 때 확장하기 좋다 | 저장 1회 = 2문장(D1 batch 필요). repo·SQL·타입·테스트 파일이 새로 는다. 지금은 칸 하나뿐이다 | 보류(운영 설정이 2개 이상 늘면 그때 분리) |

B 스키마(문안은 server-designer가 확정):

```sql
-- 0004_llm_model.sql
ALTER TABLE character_settings ADD COLUMN llm_model TEXT
  CHECK (llm_model IS NULL OR length(llm_model) BETWEEN 1 AND 20);
```

- 칸에는 **키**(`'pro'`·`'flash'`)를 저장한다. 모델명을 저장하지 않는다. 이름이 바뀌어도 데이터 이전이 없다.
- DB CHECK에 키 목록을 박지 않는다. 키 판정은 코드(`LLM_MODEL_KEYS`)가 한다. 나중에 키를 빼도 마이그레이션이 필요 없고, 표 밖 저장값은 §2.2 폴백으로 처리한다.
- UPSERT는 `llm_model = COALESCE(excluded.llm_model, character_settings.llm_model)`로 "본문에 `model`이 없으면 유지"를 한 문장에서 처리한다.
- 결과: 모델만 바꿔 저장해도 본체가 같은 값으로 다시 저장되어 version이 +1이 된다. 시드 상태(`기본값 사용 중`)에서 모델만 저장하면 시드 내용으로 행이 생겨 `isDefault: false`가 된다(D-F1, 매뉴얼에 적는다).

## 2. 결정 2 — 모델 해석·적용

### 2.1 상수표 (server `llm/models.ts` 신규)

| 키 | 화면 이름 | 모델명 |
|---|---|---|
| `pro` | Pro | `gemini-3.1-pro-preview` |
| `flash` | Flash | `gemini-3.8-flash` |

- 키 목록 `LLM_MODEL_KEYS = ['pro', 'flash']`와 타입 `LlmModelKey`는 **shared**(계약 타입)다. 모델명·단가는 **server**에만 있다.

### 2.2 해석 규칙 (순수 함수 `resolveLlmModel`)

```
입력: storedKey(D1 llm_model, 검증 전) · envModel(Config.llmModel) · envPricing(LLM_PRICE_*)
1. storedKey ∈ LLM_MODEL_KEYS        → model = 상수표[storedKey].model, source 'saved'
2. storedKey 가 NULL                  → model = envModel, source 'env'
3. storedKey 가 표 밖(코드에서 키를 뺀 경우) → model = envModel, source 'env' + error 로그 llm_model_invalid {} (값 미기록)
pricing = 단가표[model] ?? envPricing     (모델명으로 찾는다 — env가 Pro 모델명이면 Pro 단가)
응답용 키 effectiveKey = 1이면 storedKey, 아니면 상수표에서 model과 이름이 같은 키, 없으면 null
```

- D1 읽기 오류는 숨기지 않고 전파한다(settings 읽기와 같은 닫힌 실패, `500 INTERNAL`). "표 밖 값"만 폴백이다.

### 2.3 적용 시점 — 공장 함수 비동기화

```
services.ts  llm: () => Promise<Llm>
  1. requireLlmApiKey(config)                   (동기, 키 없으면 CONFIG_INVALID — D1 읽기 전)
  2. storedKey = await settings.loadModelKey()  (D1 PK 1행, SELECT llm_model)
  3. { model, pricing } = resolveLlmModel(...)
  4. createLlm({ provider: createProvider({ model }), meter: createUsageMeter({ 단가 = pricing }), modelName: model })
호출부: messages/generate.ts speak·regenerate, memory/service.ts gate → const llm = await deps.llm()
```

- speak 1회에 D1 PK 읽기 1회가 는다(수 ms, 70초 예산의 D1 여유 4초 안).
- 화자 선택과 발화는 같은 `Llm` 인스턴스라 **같은 모델**이다(R-LLM-008 문구 그대로 참).
- 요약은 `waitUntil` 안에서 자기 시작 시점에 다시 읽는다. 그 사이 주인이 바꿨으면 새 모델이다.
- 진행 중인 생성은 시작 때 읽은 모델로 끝난다.
- 기각한 안: 모델을 `generate` 호출마다 넘기는 방식. 단가가 다른 자리에서 정해져 모델과 단가가 어긋날 틈이 생긴다.

### 2.4 자동 전환 금지 · 로그

- Pro가 404·429·5xx·시간 초과를 내도 Flash로 다시 부르지 않는다. 실패는 기존 규칙(재시도 1회 → `LLM_FAILED`, 선택은 기본 화자, 요약은 건너뜀)대로다.
- 로그에 모델명을 싣는다(비밀 아님): `llm_done`·`llm_failed`·`speaker_select`에 `model` 필드. 운영에서 "고른 모델로 불렸는지"를 `wrangler tail`로 확인하는 수단이다.
- `settings_saved { mbId, version, model }`(키). 본문·필드 값은 여전히 남기지 않는다(R-SET-012).

## 6. 결정 6 — 내보내기·가져오기 제외 근거

1. **성격이 다르다.** 내보내기 파일은 "캐릭터를 옮기는 원고"다. 모델은 이 갠홈의 비용·속도를 정하는 운영 스위치다.
2. **비용 사고를 막는다.** 다른 사람이 만든 파일을 가져왔는데 모델이 Pro로 바뀌면 주인 모르게 비용이 오른다.
3. **형식 호환.** 파일 형식 `formatVersion 1`과 E.No.S 매핑(api.md §16)을 건드리지 않는다. 화이트리스트(R-SET-007)가 이미 모르는 키를 쓰지 않으므로 코드 변경은 0이고, 명시 문장과 테스트만 더한다.

## 7. 상태 흐름

```
[주인] 공통 탭 Pro 선택 → modelChanged → dirty → 「저장」
  → PUT E16 { settings, model: 'pro' } → requireToken → requireOwner → rateLimit → 상한 → zod(settings → model)
  → settings.put → UPSERT(json, …, 'pro') → 200 { settings, version+1, updatedAt, isDefault:false, model:'pro' }
  → saveSucceeded → base·modelDraft 갱신 → 「v4 저장됨」
[누구든] 버튼·전송 → speak → await llm() → SELECT llm_model → 'pro' → gemini-3.1-pro-preview · Pro 단가
  → ensureBudget → 잠금 → 읽기 → (auto면 선택 호출) → 발화 호출 → 저장 → 응답 → waitUntil 요약(다시 읽음)
```

## 12. 저쪽(갠홈) 영향 · 배포 순서

- **저쪽 재배포 없음.** 토큰·`?t=`·PHP 조각·임베드 주소가 그대로다.
- handoff 안내문 중 "설정값" 설명이 있으면 `LLM_MODEL` 뜻(고르기 전 기본값)과 `LLM_PRICE_*` 뜻(표 밖 모델용)을 1~2줄 고친다. S5 handoff 작업과 겹치므로 그 작업이 끝난 뒤 contract-designer가 반영한다.
- 우리 배포: `npm run build` → `wrangler d1 migrations apply --remote`(0004) → `wrangler deploy`. **순서를 바꾸면 speak가 500이다.** `/deploy`가 이 순서를 이미 지킨다.
- 되돌리기: 칸은 NULL 허용이라 이전 코드가 무시해도 동작한다. 코드만 이전 커밋으로 되돌려도 안전하다.
