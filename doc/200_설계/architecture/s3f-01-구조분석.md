## 1. 현재 흐름

### 1.1 모델이 정해지는 경로

```
wrangler.toml [vars] LLM_MODEL = "gemini-2.5-flash"   (.dev.vars 로컬 시험값은 gemini-3.1-pro-preview)
  → server/src/env.ts parseEnv: MODEL_PATTERN ^[A-Za-z0-9._-]{1,64}$, 기본값 'gemini-2.5-flash' → Config.llmModel
  → server/src/services.ts createServices: const llm = (): Llm => createLlm({ provider: createProvider({ model: config.llmModel }) , meter: createUsageMeter({ 단가 = config.llmPriceInput/OutputUsdPerM }) })
  → server/src/llm/factory.ts → GeminiProvider({ apiKey, model })
  → server/src/llm/gemini.ts: POST {BASE}/models/{model}:generateContent
```

- 모델은 **배포 단위 고정값**이다. 바꾸려면 `[vars]`를 고치고 다시 배포해야 한다.
- 단가도 env 한 쌍(`LLM_PRICE_INPUT_USD_PER_M=0.3` · `LLM_PRICE_OUTPUT_USD_PER_M=2.5`, 2.5-flash 기준)뿐이다. 모델과 단가가 따로 논다.
- 비용 누적(`llm/usage.ts` `record`)은 호출마다 `estimateKrw(usage, pricing)`로 원화를 계산해 `llm_usage` 월 행에 더한다. 누적값은 호출 시점 단가로 굳는다.

### 1.2 LLM을 부르는 세 경로와 공장 함수 호출 시점

| 경로 | 위치 | 순서 |
|---|---|---|
| speak(버튼·자동) | `server/src/messages/generate.ts` 138행 | `deps.llm()` **동기** → `ensureBudget` → 잠금 → `Promise.all(pageDesc ∥ getSummary ∥ loadPromptSettings)` → (`'auto'`면 `selectSpeaker`) → `complete` |
| regenerate | 같은 파일 185행 | `deps.llm()` → `ensureBudget` → 잠금 → 읽기 3종 → `complete` |
| 요약(S4) | `server/src/memory/service.ts` 107행 `gate` | speak 응답 뒤 `waitUntil` 안에서 `deps.llm()` → `ensureBudget` → `complete(budgetMs 25초)` |

- 세 경로 모두 `services.ts` 63행의 **같은 `llm` 클로저**를 쓴다. 화자 선택 호출도 같은 `Llm` 인스턴스라 같은 모델이다.
- 공장 함수는 **D1을 읽기 전에, 동기로** 불린다. 모델을 D1 값으로 고르려면 이 함수가 D1을 먼저 읽어야 한다.
- 캐릭터 설정 읽기(`settings.loadForPrompt`)는 이미 speak마다 D1 PK 1행을 읽는다(캐시 없음, R-SET-003). "저장 즉시 다음 호출부터 반영" 패턴이 있다.

### 1.3 설정 저장·읽기 경로 (S3c)

```
화면 StatusBar 「저장」 → useSettingsEditor (122행) saveCharacterSettings(check.value)
  → ui/src/api/settings.ts PUT { settings }  (auth: true)
  → server/src/routes/settings.ts: requireToken → requireOwner → rateLimitWrites → bodyLimit(128KB) → validate(zod) → settings.put(body.settings, principal)
  → server/src/settings/service.ts put: parseCharacterSettings 재검증 → db.characterSettings.upsert(json, mbId, now)
  → server/src/db/sql.ts SQL_CHARACTER_SETTINGS_UPSERT (id = 1, version + 1, RETURNING version, updated_at)
  → 응답 CharacterSettingsResponse { settings, version, updatedAt, isDefault }
GET E15 → settings.get → readCurrent: 행 없음·재검증 실패면 시드(isDefault true, version 0)
```

- 테이블 `character_settings`(마이그레이션 0003): `id(=1) · json · version · updated_at · updated_by`. 본체 JSON은 strict(R-SET-002).
- E16 봉투(`settings` 바깥)의 모르는 키는 버린다(api.md §4.5). 응답 키는 정확히 넷이다(api.md §4.15, `routes-settings.test.ts` 159행 단언).
- 엔드포인트는 16개 고정이다(R-API-001 🔒). 주인 판정은 E15 status로만 한다(§2.7).

### 1.4 설정 화면 (ui)

```
SettingsScreen(index.tsx) → ReadyBody → Tabs(공통 세계관 · 세바스찬 · 시엘) → FormPanel
   'world' → WorldForm (세계관 TextArea 하나, maxRows 16)
   캐릭터  → CharacterForm (11필드)
   StatusBar(D 36px): 상태 문구 + 「되돌리기」 + 「저장」
상태(ui/src/state/settings.ts): ReadyState { base: CharacterSettingsResponse, draft: SettingsDraft, isSaving, isStale }
   dirty = isDraftDirty(draft, base.settings) — canRevert · canSave · statusOf · 이탈 확인(useSettingsUi 82행)이 이것을 쓴다
   내보내기 = exportTargetOf(state) → base.settings(CharacterSettings)만 화이트리스트 직렬화(api.md §16.1)
   가져오기 = SettingsPatch를 draft에 덮는다(settings 위치만)
```

- 공용 ui에 라디오 컴포넌트가 없다(`ui/src/components/ui/`: Button·IconButton·TextArea·TextInput·Toggle 등).
- 화면 코드의 `<input>`은 공용 ui와 로컬 `Tabs`·`FilePicker`에만 허용된다(settings components.md 머리말).
- 탭 이름은 `labels.ts` 107행 `tabLabel.world = '공통 세계관'`이다. 요구 R-SET-009 표기는 "공통".

## 2. 문제점·제약

| # | 문제·제약 | 설계에 주는 영향 |
|---|---|---|
| P1 | 모델이 요청 앞에서 동기로 정해진다(1.2) | 공장 함수를 `() => Promise<Llm>`으로 바꾸거나, 모델을 호출마다 넘겨야 한다. 전자는 단가도 같은 자리에서 정해져 일관된다 |
| P2 | env 기본값 `gemini-2.5-flash`가 신규 키에서 404다 | "저장값이 없을 때 쓰는 기본값"이 고장 난 상태다. 기본값 교체가 필요하다(사용자 결정 — 가벼운 모델로 몰래 바꾸기 금지 2026-10-06) |
| P3 | 단가가 env 한 쌍뿐이다 | 모델을 바꾸면 비용 추정이 틀린다. Pro는 Flash보다 비싸 월 상한(R-LLM-007)이 늦게 걸릴 수 있다 |
| P4 | 설정 본체 JSON은 strict이고 내보내기는 화이트리스트다 | 모델을 본체에 넣으면 R-SET-002·R-SET-007·가져오기 매핑이 함께 흔들린다 |
| P5 | 엔드포인트 16개 고정(R-API-001 🔒) | 새 엔드포인트보다 E15·E16 확장이 맞다. 응답 키 추가는 "정확히 넷" 단언을 고친다 |
| P6 | Pro는 느리다(사고 토큰) | 화자 선택 15초·요약 25초·speak 66초 예산 안에서 실패가 늘 수 있다. 실패는 기존 규칙대로 기본 화자·요약 건너뜀·`LLM_FAILED`다 |
| P7 | 라디오 공용 컴포넌트 없음 · `<input>` 사용 위치 제한 | 로컬 컴포넌트 1개를 새로 두고 예외 목록에 올려야 한다 |
| P8 | 테스트가 `llm: () => Llm`을 동기로 주입한다 | `messages-generate.test.ts` 4곳 · `memory.test.ts` 2곳 · `helpers.ts` 1곳이 비동기 시그니처로 바뀐다 |
| P9 | 동시 작업자 | 지금 contract-designer가 `doc/handoff/**`·api.md §8·§9를, server-implementer가 `server/scripts/**`를 쓰고 있다. S3f의 api.md 편집은 S5 handoff 편집이 끝난 뒤에 시작해야 한다 |
| P10 | 배포 순서 | speak마다 새 칸을 읽는다. 코드가 마이그레이션보다 먼저 올라가면 speak가 `500 INTERNAL`이다. `/deploy` 순서(마이그레이션 → deploy)를 지켜야 한다 |
