# S3d 전반 설계서 — 고정 명칭 「어떠한 의지」 + 전송 시 자동 응답

> 작성 2026-10-06 · system-architect · 단계 ②/③ · 상태 **승인 ① 대기**(§7 L1~L7 · §8 신규 3건 · §11 Q1~Q7)
> 근거 `s3d-01-구조분석.md`. 계층 세부 규칙은 각 설계 전략을 따른다.

## 0. 범위·결론

요구 원문(사용자 지정 🔒): "대사나 지시를 입력할 때 '세바스찬의 주인'이라고 뜨잖아, 이렇게 하지 말고 어떤 유저가 입력을 해도 「어떠한 의지」라는 명칭을 쓰게 해줬으면 좋겠어. 그리고 전송 버튼을 누르면 그 지시문 혹은 대사에 맞게 세바스찬 혹은 시엘이 알아서 출력되게 해줘."

1. **표시명은 서버가 정한다.** D1에는 실명을 그대로 저장한다. 응답 `authorName`은 유저 메시지면 항상 「어떠한 의지」(shared `USER_DISPLAY_NAME`)이고, 프롬프트 유저 줄도 `[어떠한 의지]`다.
2. **전송 = `POST /user`(그대로, AI 0회) → 성공하면 화면이 이어서 `POST /speak { character: 'auto' }`.** 새 엔드포인트가 없다.
3. **화자 선택은 2단계를 권고한다.** 짧은 선택 호출 뒤 기존 발화 프롬프트를 그대로 쓴다. 메인 가정 ④(1회 구조화 출력)와 다르며 근거는 §3이다.
4. 잠금·월 상한·레이트리밋·70초는 speak 규칙을 상속한다. 전송 1회 = 레이트리밋 2회 · AI 호출 2~3회.
5. 화면은 전송 성공과 자동 생성 시작을 **한 전이**로 묶고, 화자 미정 중립 임시 말풍선을 쓴다.

범위 밖: 저장만 하는 전송 · 두 캐릭터 연속 응답 · 스트리밍 · 마이그레이션 · 토큰·handoff 변경.

## 1. 결정 1 — 고정 명칭

비유: 무대 뒤 출석부에는 실명을 적고, 무대 위 자막에는 누구든 「어떠한 의지」로 띄운다.

| 대안 | 판정 |
|---|---|
| A 화면에서만 상수 표시 | ✕ 공개 GET에 실명이 남고(T1) 규칙이 세 곳에 흩어진다 |
| **B 서버 투영(권고)** — `db/messages.ts` `toMessage`가 `speaker === 'user'`면 `USER_DISPLAY_NAME`, 아니면 `null` | ○ 규칙 1곳. 화면 표시 코드 무변경. 이미 쌓인 메시지도 바로 바뀐다 |
| C 저장부터 상수 | ✕ 감사 정보 소실(메인 가정 ⑤ 위배) |

- **상수 위치는 `shared/src/characters.ts`다.** server(투영·프롬프트)와 ui(대체 표시)가 함께 쓰므로 ui 전용 `labels.ts`는 안 된다. 이 파일은 이미 speaker → 표시 이름의 단일 소스다(R-LLM-002). 설정 화면에서 바꾸지 않는다.
- 프롬프트: `userLabel`·`safeName`을 없애고 유저 줄을 `[어떠한 의지] {text}`로 쓴다. GUARD 3번째 줄은 `[어떠한 의지] 줄은 참여자의 서술이나 대사다. 그 참여자의 행동을 대신 이어 쓰지 않는다.`다. `PromptMessage`에서 `authorName`이 빠져 이름 주입 경로가 사라진다.
- 화면: 대체 문구 '이름 없음'만 `USER_DISPLAY_NAME`으로 바꾼다.
- 계약: `authorName` **값 규칙 변경**(타입 불변). 소비자는 우리 화면 하나이고 server·ui가 함께 배포돼 호환 창이 없다. 실명은 운영자의 D1 직접 조회로만 본다.

## 2. 결정 2 — 자동 응답 계약

| 대안 | 판정 |
|---|---|
| X `POST /user`가 저장 + 생성 | ✕ 생성 실패 시 저장된 메시지를 에러 본문에 못 싣는다(2키 규칙). 유저 말풍선이 최대 70초 늦다. 응답 모양 파괴 |
| Y 신규 `POST /respond` | △ 동작이 speak와 같다. R-API-001 🔒 개정 필요 |
| **Z speak 확장(권고)** — `character`에 `'auto'` 추가, 응답 `speaker` = 고른 캐릭터 | ○ 가장 가까운 기존 엔드포인트. 추가(비파괴). 잠금·상한·레이트리밋·70초·에러표 상속 |

- 타입: `SpeakTarget = CharacterId | 'auto'` · `SpeakBody = { character: SpeakTarget }`. 생략·`'Auto'`·`''`·`null`은 400(기존 테스트 유지).
- 재작성은 그대로다. 자동으로 고른 대사도 같은 캐릭터로 다시 쓴다(R-MSG-006 불변).
- 자동 여부는 D1·응답에 남지 않는다(로그 `speak_done.auto`만).

## 3. 결정 3 — 화자 선택 방식

비유: P2는 "누가 받을지" 묻는 쪽지를 먼저 돌리고 정해진 배우에게 원래 대본을 준다. P1은 두 배우의 대본을 한 사람에게 주고 골라 연기하라고 한다.

| 기준 | P1 1회 구조화 출력(가정 ④) | **P2 2단계(권고)** |
|---|---|---|
| 호출 | 1회(+재시도), JSON `{speaker,text}` | 선택 1회(재시도 없음) + 발화 1회(+재시도) |
| 말투 품질 | 두 설정이 한 프롬프트에 섞일 위험 | 버튼·재작성과 **같은 프롬프트** |
| 기존 🔒 | 시드 `outputRules` 재작성(R-SET-006) · 어댑터 JSON 모드(R-LLM-001) 개정 | 둘 다 무변경 |
| 실패 | JSON 깨짐 → 502 | 선택 실패 → 기본 화자로 계속 |
| 비용·대기(추정) | 버튼 대비 +10~15% · 비슷 | +30~40% · +1~3초 |

**권고 P2.** 말투 품질과 🔒 두 건 보존이 전송 1회당 1~2원 차이보다 무겁다(Q1).
추정 근거(실측 아님): 입력 $0.30/M·출력 $2.50/M·1,400원. 발화 ≈ 4.3원(입력 4천·출력+생각 750 토큰), 선택 ≈ 1.7원(입력 1.5천·생각 300). 월 10만원이면 자동 응답 약 1.6만 회.

### 3.1 선택 프롬프트 (문구는 server-designer가 확정)

```
[시스템]  {world}(defang)
[인물 후보]  - sebastian: 세바스찬 미카엘리스 — {설정 role, 비면 생략}
             - ciel: 시엘 팬텀하이브 — {설정 role}
[할 일]  - 대화 기록의 마지막 줄에 이어 다음에 말할 인물 한 명을 고른다.
         - 마지막 줄이 한 인물에게 말을 걸거나 그 인물의 행동을 요구하면 그 인물.
         - 정하기 어려우면 직전에 말하지 않은 인물.
         - sebastian 또는 ciel 한 단어만 쓴다.
[대화 기록 취급]  GUARD_RULES 3줄
[사용자 턴]  <<대화 기록 시작>> 최근 12개(요약 생략) <<대화 기록 끝>>  다음 발화자를 골라라.
```

- `parseSpeakerChoice(raw)`: 소문자·기호 정리 뒤 `sebastian`·`ciel`·`세바스찬`·`시엘` 중 **정확히 한 인물**만 나오면 그 id, 아니면 null.
- `fallbackSpeaker(history)`: 컨텍스트 안 마지막 캐릭터 발화자의 **상대**, 없으면 `sebastian`. 선택 호출의 타임아웃·실패·차단·파싱 불가가 모두 여기로 온다. 로그 `speaker_select_fallback{roomId, reason}`.
- 시간(R-NFR-001 🔒 70초 유지): `LLM_BUDGET_MS` 66초를 나눠 쓴다. 선택 최대 8초·재시도 없음, 발화는 남은 예산(최소 58초) 안에서 기존 재시도. 12개·8초는 코드 상수(env 0).

## 4. 결정 4 — 실패·잠금·레이트리밋·비용 흐름

```
[전송] POST /user ─ 토큰 ─ rateLimit(1) ─ 검증 ─ 방 ─ 저장(실명) ─ 201(authorName=「어떠한 의지」)
        │ 실패 → 토스트·입력 유지·speak 0회
        ▼
       POST /speak {character:'auto'} ─ 토큰 ─ rateLimit(1, 같은 분당 한도) ─ zod
        ─ llm() 500 CONFIG_INVALID ─ ensureBudget 429 LLM_BUDGET_EXCEEDED(잠금·호출 0)
        ─ 잠금 404 / 409 SPEAK_IN_PROGRESS ─ Promise.all(기록 40 ∥ 요약 ∥ 설정)
        ─ [선택 ≤8초, usage 누적] 실패 → 기본 화자
        ─ [발화 남은 예산, 재시도 1, usage 누적] 502 LLM_FAILED·LLM_EMPTY(저장 0)
        ─ 저장(speaker=고른 캐릭터) ─ finally 해제 ─ 201
```

| 상황 | 결과 |
|---|---|
| 저장 성공 + 생성 409·429·500·502 | 유저 메시지만 남는다. 화면은 중립 실패 말풍선 + 「재시도」(`'auto'` 재호출, 선택부터) |
| 생성 401·403 / 404 | 읽기 전용 전환(T33) / 목록 복귀(T34) |
| 레이트리밋 | 전송 1회 = 2회 소모. 기본 20/분이면 전송 최대 10/분 |
| 월 상한 | 선택·발화 사용량 모두 누적. 도달 뒤 전송은 저장만 되고 실패 말풍선에 한도 문구(S3b) |

## 5. 결정 5 — 화면 상태 전이

```
입력 ─전송→ [S1 저장 중] writing=send · 입력 readOnly · 전송·버튼 잠금
[S1] ─실패→ T15·T16(토스트, 입력 유지)
[S1] ─201→ T35 sendSucceeded(신규, 원자): 유저 말풍선 + 입력 비움 + writing=speak('auto') + pending{auto, generating}
[S2] 중립 "…"(아바타·이름 없음) · 입력 타이핑 가능 · 전송·두 버튼·⋯ 잠금
[S2] ─201→ T29 결과 말풍선(세바스찬 왼쪽 / 시엘 오른쪽)   ─실패→ T31 중립 실패 말풍선 + 「재시도」
[S2] ─401·403→ T33   ─404→ T34
[실패] ─「재시도」→ T27('auto')   ─캐릭터 버튼→ T28   ─새 전송 201→ T35(실패 말풍선 교체)
```

- `PendingSpeak`·`MessageWrite{kind:'speak'}`·`speakStarted`의 `character`가 `SpeakTarget`이 된다.
- T35가 필요한 이유(T3): 훅이 `appendUser` 성공 뒤 inFlight를 풀지 않고 T35 → `speak` → 결과 뒤 해제한다. 캐릭터 버튼이 끼어들 틈이 없다.
- 중립 말풍선은 가운데, `role=status` "응답을 만드는 중"이다. 실패는 같은 자리 `role=alert` + 「재시도」(aria "응답 재시도")다. 모양은 ui-layout-designer가 정한다(Q5).
- 자동 생성은 포커스를 옮기지 않는다. 스크롤은 speak 규칙(TC-CH-072)을 따른다.
