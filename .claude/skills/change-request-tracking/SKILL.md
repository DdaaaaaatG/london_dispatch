# 변경 요구 추적 (CR 대장) 표준

- 목적: 화면마다 "무엇을 요구했고 무엇을 반영했는가"를 누적 기록하고, 다음 변경 요구를 **이전 이력과 충돌 없는 상태**에서 처리한다.
- **보강(maintain) 모드 전용.** 구축(build) 모드의 신규 화면 생성은 대상이 아니다 — 요구 baseline은 `requirements.md`가 소유한다.
- 적용 진입점: 메인 세션 직접 수정(fast-path) · ui-debug · ui-fixer · ui-implementer(보강) · ui-manager 보강 흐름 **전부**.

## 1. CR 대장 정의

- 위치: `ui/src/{screen}/test/change-requests.md`(screen ∈ rooms, chat) — 첫 기록 시 생성(소급 생성 안 함).
- 성격: **append-only 기록물(ledger)**. 과거 엔트리는 삭제·수정 금지, **상태 마킹만** 바꾼다.
- 소유 경계: 요구 baseline = `requirements.md`(R-xx), TC = `test/scenarios.md`(TC-xxx). CR 대장은 이들과 **ID로 상호 링크**하는 이력이다(내용 중복 금지).

### 엔트리 필드

| 필드 | 규칙 |
|---|---|
| CR-ID | `CR-001`… 화면별 연번. 재사용 금지 |
| 일자 | yyyy-mm-dd |
| 출처 | 사용자 직접(🔒) / 지인 피드백 / 버그 신고 / contract 계약 변경(api.md 버전) / 검증 지적(verify) |
| 요구 | 사용자 요구 원문 한 줄 |
| 확정 해석 | 인터뷰·추론으로 확정한 내용 |
| 조치 | 변경 파일 · 추가/수정 TC(TC-ID) · 관련 요구ID(R-xx) |
| 상태 | **적용·미검증** → **검증됨(yyyy-mm-dd)** → (대체 시) **폐기(CR-nnn로 대체, 확정 yyyy-mm-dd)** |
| 충돌 메모 | 충돌한 CR-ID + 확정 결과(없으면 공란) |

### 템플릿 (첫 생성 시)

```markdown
# {화면명} 변경 요구 이력 (CR 대장)

append-only. 과거 엔트리는 상태 마킹만 변경. 규약: .claude/skills/change-request-tracking/SKILL.md

| CR-ID | 일자 | 출처 | 요구 | 확정 해석 | 조치 | 상태 | 충돌 메모 |
|---|---|---|---|---|---|---|---|
```

- 최신 엔트리를 표 **아래에 append**한다.
- 폐기 엔트리는 상태 열에 `폐기(CR-nnn로 대체, 확정 yyyy-mm-dd)`를 쓰고 행은 남긴다(취소선 불필요).

## 2. 조회·충돌 검사 (작업 시작 전 필수)

1. **이력 조회**: 대상 화면 `test/change-requests.md`를 Read(+ `requirements.md`의 🔒 요구). 파일이 없으면 "이력 없음"으로 진행.
2. **충돌 판정**: 신규 요구 vs **활성**(적용·미검증/검증됨) CR만 대조(폐기 CR 제외).
   - **정면 충돌**: 이전 요구를 뒤집는다(예: CR-002 "OOC 토글 숨김" ↔ 신규 "OOC 토글 표시").
   - **부분 충돌**: 같은 요소·겹치는 범위를 다른 방향으로 바꾼다(예: 롱프레스 "500ms" ↔ "300ms").
   - **무관**: 겹침 없음.
3. **무충돌** → 이력 맥락(과거 요구·결정 이유)을 반영한 해결 방안을 제시하고 진행한다.
4. **충돌** → 3절 인터뷰로 확정하기 전에는 수정을 시작하지 않는다.

## 3. 충돌 확정 (사용자 인터뷰)

- 이전 CR 원문과 신규 요구를 **나란히 제시**하고 확정받는다. 선택지: ① 신규 우선(구 CR 폐기) ② 이전 유지(신규 철회/조정) ③ 절충(내용 명시).
- 인터뷰 주체 = **메인 세션/매니저만**(`AskUserQuestion`). 서브에이전트로 호출된 경우 충돌 발견 시 정지 → 「충돌 확인 필요」(이전 CR 원문 + 신규 요구)를 최종 응답으로 보고 — 호출자가 인터뷰한다.
- 지인(발주자) 피드백이 사용자 🔒 요구와 충돌하면 사용자가 지인과 확인한 뒤 답한다. 에이전트가 지인 의도를 추측하지 않는다.
- 확정 후 반영:
  - 구 CR → 상태 `폐기(대체 CR-ID, 확정일)`. 신규 CR 기록(충돌 메모에 상대 CR-ID·확정 결과).
  - 관련 🔒 요구·TC 조정의 승인 근거로 **CR-ID를 남긴다**. `requirements.md`의 옛 요구 행은 삭제하지 않고 `폐기(CR-nnn으로 대체)` 마킹.

## 4. 조치 기록 (완료 시 필수)

- **소스 변경을 완료한 주체가 append**한다: fast-path = 메인 세션, ui-debug/ui-fixer = 자신, ui-manager 흐름 = 위임받은 구현 에이전트(위임 프롬프트의 CR 초안 사용).
- 소스 반영 시점에 상태 **「적용·미검증」**으로 기록한다. 같은 패스에서 `test/scenarios.md` 「변경 대기열」 절에 `Q-nn` 행(CR-ID · 변경 요약 · 변경 파일 · 영향 TC 후보 · 신규 TC 필요 여부 · 상태 `대기`)을 append한다.
- **검증 후 마킹**: 관련 TC 통과(ui-tester 증거) 또는 `/doc-sync` 전건 통과 시 상태를 「검증됨(yyyy-mm-dd)」로, 대기열 행을 「검증됨」으로 바꾼다. 통과 전에는 마킹하지 않는다.
- **CR 기록 없이 완료 보고 금지.** 커밋 메시지에 CR-ID를 남긴다(`/doc-sync`가 git history↔CR 대장을 대조·backfill).

## 5. 연계

- **ui-test-designer**: 변경 대기열 행을 TC로 전환할 때 TC 출처에 CR-ID를 병기한다(R-xx와 함께).
- **ui-designer(동기화 모드)**: design.md 변경이력에 CR-ID별 행을 남긴다.
- **/doc-sync**: git history와 CR 대장을 대조 — 수정은 있는데 엔트리가 없으면 커밋 메시지로 backfill.
- **contract 계약 변경**: api.md 버전이 올라 화면에 영향이 있으면 출처 `contract 계약 변경(v n)`으로 CR을 기록한다. 토큰 형식 변경은 handoff 재적용과 함께 기록.

## 6. 수정 경로 라우팅 (fast-path vs ui-debug)

| 작업 유형 | 라우팅 | 검증 |
|---|---|---|
| 표시 변경(문구·간격·색·오타), 단순 로직, props 조정, 가벼운 상태/이벤트 수정 | **메인 세션 직접(fast-path)** — 단 CLAUDE.md §5-0 위임 원칙상 사용자가 "직접 고쳐"라고 명시한 때만 | 앱 실행·스크린샷 + 관련 vitest |
| contract 계약 변경이 수반되는 수정, 비자명한 원인 추론(RCA), 여러 모듈에 걸친 수정 | **ui-debug** | 자신이 고친 것만 타깃 검증 |
| 새 화면·새 기능·구조 재설계 | ui-manager | — |
| server·contract 원인 | server-manager / contract-manager 세션 인계 | — |

- fast-path도 CR 조회·기록·대기열 행은 동일하게 수행한다.
- **작업 국소화**: 화면 수정은 `ui/src/{screen}/` 안에서만이 기본. 공용 컴포넌트·`ui/src/state`에 걸치면 사용자 인터뷰 후에만. `ui/src/api`는 ui 에이전트가 쓰지 않는다(contract 인계).

## 경계·금지

- 구축(build) 모드 신규 화면 생성에는 적용하지 않는다.
- 과거 엔트리 삭제·재작성 금지(상태 마킹만). CR-ID 재사용 금지.
- 대장은 마크다운 표 하나로 유지한다(HTML·JSON 금지).
