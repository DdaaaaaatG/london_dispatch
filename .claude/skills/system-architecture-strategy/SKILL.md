# 시스템 아키텍처 전략

- 횡단 기능을 다루는 **단일 기준**. `system-architect`가 이 규칙으로 판단한다.
- 계층 전략(server/contract/ui-design-strategy)=각 계층의 생산 규칙, 이 전략=세 계층을 가로질러 **먼저 구조를 잡는 사전 설계** 규칙. verify-strategy(배포 직전 게이트)와 짝이되 이쪽은 **착수 이전** 게이트다.

## 0. 핵심 원칙

1. **횡단 먼저.** 시스템 전반 기능을 한 계층 관점으로 들어가면 임시방편이 나온다. 전 계층을 가로질러 구조를 먼저 본다.
2. **분석→전반설계→분해 순서 고정.** 구현 설계로 바로 뛰지 않는다.
3. **읽기 전용.** 아키텍트는 측정·설계만 한다. 소스·설정 수정 금지. 구현은 매니저(server/contract/ui-manager)로 인계.
4. **단일 소스 존중.** 계층 세부 규칙은 각 전략을 **참조**한다. 재정의 금지.
5. **종단간 추적.** 모든 결론은 요구→ui→contract→server→env 키가 끊김 없이 이어지는 RTM으로 닫는다.
6. **단방향 인계·세션 분리.** 인계는 server→contract→ui. 분석·설계와 구현은 세션을 나눈다.

## 1. 횡단 판별 기준

| 신호 | 횡단(이 전략) | 단일(매니저) |
|---|---|---|
| 건드리는 계층 수 | 2개 이상 | 1개 |
| speak 파이프라인 | 요청→프롬프트 조립→LLM→후처리→저장→요약의 구조·순서 자체를 바꿈 | 한 지점의 버그·상수 조정 |
| 계약 | 기존 엔드포인트 필드 제거·의미 변경, 토큰 payload·서명 변경 | 필드 추가·새 엔드포인트 |
| DB 스키마 | speaker·kind 종류 추가, 테이블 분리·병합, 데이터 이관 | 컬럼 1개 추가(기본값 있음) |
| 캐릭터 | 수·구조 변경(3명째, 캐릭터별 설정 관리 화면) | persona 문구 수정 |
| 권한 | 등급 외 새 권한 모델(방 소유자, 관리자 전용 동작) | `TOKEN_MIN_LEVEL` 값 변경 |
| 증상 | 같은 판정 로직이 server와 ui에 중복(예: 재작성 가능 조건) | 국소 결함 |

- 단일이면 즉시 해당 매니저로 안내한다(화면=ui-manager, 계약=contract-manager, 서비스=server-manager).
- 애매하면 영향 후보(모듈·엔드포인트·화면)를 훑어 계층 수를 센 뒤 판정한다.

## 2. 3단계 방법론

### 2.1 구조 분석 (현황, 읽기 전용)
- `server-analyst`·`contract-analyst`를 **병렬 위임**해 현황·표준 준수·영향을 받는다(요약 + 리포트 파일 경로, 경로는 서로 다르게 지정).
- ui는 직접 읽는다: 화면 `design.md`, `ui/src/state/*.ts`, `ui/src/api/*.ts`.
- 산출: **구조 분석서** — 현재 데이터 흐름 다이어그램(텍스트), 엔드포인트 목록, 대화 상태 전이(상태·이벤트·전이), DB 스키마, env 키, 문제점·제약·중복.

### 2.2 전반 설계
- 요구를 종단간으로 재정렬한다. 대안이 갈리면 근거를 양쪽 다 적고 사용자 결정(`AskUserQuestion`).
- 판단 기준 예: 판정 로직은 **한 곳**(원칙: 권한·재작성 가능·요약 시점은 server, 표시 분기·스크롤은 ui, 둘이 같은 값을 알아야 하면 응답 필드로 내려준다). 유저 텍스트는 시스템 프롬프트에 섞지 않는다. 캐릭터 설정은 server 상수가 소유하고 ui는 응답으로 받는다.
- 산출: **전반 설계서** — 목표 구조, 상태 전이 확정본, 계약 변경 목록(추가/변경/폐기 + 하위 호환 여부 + 저쪽 재적용 여부), DB 스키마 변경(마이그레이션 번호·이관), env 키 변경, 종단간 RTM.

### 2.3 계층별 구현 설계 분해
- 계층마다 **인계 패킷** 1개. 각 패킷은 그 매니저가 **그것만 읽고** 시작할 수 있어야 한다.

| 요구ID | 요구 | ui | contract | server | env 키 | 테스트 | 상태 |

- 어느 열이든 끊기면 미완. 해당 없음은 `-`.

## 5. 인계 규약

- 순서 **server → contract → ui**. 앞 계층의 완료 마커가 뒤 계층의 착수 조건.
- 각 매니저 세션은 자기 패킷만 읽고 자기 전략으로 일한다. 패킷에 없는 것을 추측해 만들지 않는다 — 부족하면 아키텍트 세션으로 되돌린다(왕복은 아키텍트 세션에서만).
- 계약 파괴 변경은 contract 패킷에 **하위 호환 전략**(동시 지원 기간·폐기 시점)과 **저쪽 전달 계획**(토큰 변경 시 PHP 조각 재적용 순서 — 서버가 옛·새 형식을 동시에 받는 기간)을 명시한다.

## 6. 세션 분리

- 분석·설계(아키텍트) / server 구현 / contract 구현 / ui 구현 / verify는 **각각 별도 세션**.
- 한 세션에서 두 계층을 구현하지 않는다(컨텍스트 50% 규칙).
